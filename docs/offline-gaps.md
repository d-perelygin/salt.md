# Оффлайн: баги и улучшения текущей поддержки

Аудит ветки `analyze_offline_support_gaps` (HEAD `e4e42b8`), 2026-11-25/26.
Правки в продукт не вносились; для проверки каждого пункта запускались
воспроизводящие Playwright/Node/HTTP-пробы против собранного бинарника
(`tmp/verify/`). Каждый пункт помечен:

- **[подтверждено тестом]** — воспроизведено запуском против реального сервера/браузера;
- **[код]** — подтверждено чтением кода (инфраструктурное ограничение или документация, не требующее отдельного прогона).

Приоритеты: **P0** — потеря или порча данных; **P1** — сломанная функция или
утечка между аккаунтами; **P2** — дыра в UX оффлайна; **P3** — полировка,
документация.

## Как устроено сейчас (кратко)

| Слой | Где | Что делает |
| --- | --- | --- |
| Service worker | `web/public/sw.js` | shell (`/`) + `/assets/*` cache-first; GET `/api/me`, `/api/workspaces`, `/api/pages*`, `/api/collections*`, `/api/templates` network-first с фолбэком на кэш |
| IDB снапшоты | `web/src/offlineCache.ts` | `pages`, `collections` (замороженный вид), `ydocs` (полный Y-state), БД на аккаунт |

## P0 — потеря и порча данных

### 1. `appendJournal` теряет апдейты при быстром наборе [подтверждено тестом]
> **Тест (`batch1_crdt.mjs`):** 60 символов набраны оффлайн без задержки → `yjournal.updatesLen = 2`; после reconnect второй чистый контекст увидел только `"a"` (59 символов потеряно).

[offlineCache.ts#L288-L300](../web/src/offlineCache.ts#L288-L300): чтение записи
журнала и запись идут в **двух разных транзакциях** (`readonly`, потом
`readwrite`). Каждое нажатие клавиши — отдельный Y-апдейт и отдельный
`void appendJournal(...)`; параллельные вызовы читают одну и ту же версию и
перезаписывают друг друга, выживает последний `put`.

Последствие хуже, чем «пропала буква»: Yjs-апдейты причинно зависят друг от
друга. Если на сервер ушли апдейты N и N+2 без N+1, то N+2 у сервера и у всех
пиров зависает в pending навсегда. Текст есть только в локальном doc и
частично лечится случайным `snapshotRequest`.

Почему тест не ловит: [offline.mjs](../web/tests/offline.mjs) проверяет
`GET /api/pages/:id` (это материализованный `pages.content`, приходит через
outbox), а не CRDT; после reload текст рисуется из локального `ydocs`-снапшота.

**Фикс:** read-modify-write в одной `readwrite`-транзакции (или хранить каждый
апдейт отдельной записью с автоинкрементом); лучше сливать через
`Y.mergeUpdates`. **Проверка:** unit/браузерный тест: 200 апдейтов параллельно →
`readJournal().length === 200`; e2e: набрать оффлайн, переподключиться,
открыть страницу во **втором чистом контексте** и сравнить текст.

### 2. Обрезка журнала до 1000 ломает причинность [подтверждено тестом]
> **Тест (`batch2_outbox.mjs`):** 1005 последовательных Yjs-апдейтов обрезаны до последних 1000 → `Y.applyUpdate` в чистый `Y.Doc` дал длину текста `0` (все 1000 апдейтов зависли в pending).

[offlineCache.ts#L286-L295](../web/src/offlineCache.ts#L286-L295):
`while (updates.length > MAX_JOURNAL) updates.shift()` выбрасывает **самые
старые** апдейты. После ~1000 нажатий оффлайн все последующие апдейты зависят от
выброшенных, и сервер их применить не может: теряется весь хвост.
**Фикс:** вместо обрезки сжимать журнал (`Y.mergeUpdates`) по порогу.

### 3. Журнал очищается без подтверждения доставки [подтверждено тестом]
> **Тест (`batch2_outbox.mjs`):** WS-перехватчик пропустил `synced`, но оборвал сокет на первом бинарном `FRAME_UPDATE` → `yjournal` очистился (`6 → 0`), второй чистый контекст увидел только `"BASE_3"`, оффлайн-текст `"_LOST3"` потерян.

[collab.ts#L182-L185](../web/src/collab.ts#L182-L185): после `synced` журнал
отправляется через `ws.send`, а затем `clearJournal`. Подтверждения от сервера
нет: если сокет умер сразу после отправки (типичный флапающий канал), апдейты
потеряны. Кроме того, `clearJournal` удаляет запись целиком, включая апдейты,
дописанные между `readJournal` и `clearJournal` (окно гонки с п. 1).

**Фикс (предпочтительно):** на каждом `synced` отправлять
`Y.encodeStateAsUpdate(doc)` целиком (Yjs-слияние идемпотентно), а от
переписанного документа защищает уже существующий `gen`-фенс. Журнал тогда не
нужен вовсе. Если оставлять журнал — нужен ack от сервера (seq) и удаление
только подтверждённого префикса.

### 4. Снапшот `ydocs` без `gen` — четвёртая «дверь» для старого документа [подтверждено тестом]
> **Тест (`batch1_crdt.mjs`):** страница с `"OLD_V1"` закрыта, агент переписал её на `"AGENT_V2"` (`doc_gen++`, `resetYjsDoc`). При повторном открытии онлайн браузер X загрузил `"OLD_V1"` из `ydocs` и полностью затёр `"AGENT_V2"` (сид не сработал на непустом фрагменте).

`server/docgen.go` описывает три способа вернуть старое тело поверх
переписанного (agent/MCP/restore/import → `resetYjsDoc`). Оффлайн-кэш
открывает четвёртый:

1. Страница открыта в браузере X, на unmount сохранён полный Y-state
   ([Editor.tsx#L2838-L2841](../web/src/components/Editor.tsx#L2838-L2841)).
2. Агент переписывает страницу, CRDT-doc сервера выброшен, `doc_gen++`.
3. X открывает страницу (даже **онлайн**): `getPage` даёт новый `docGen`,
   `getYDoc` — старый снапшот, он применяется в
   [collab.ts#L75-L81](../web/src/collab.ts#L75-L81), подключение с новым `gen`
   принято, сервер реплеит новый doc → локально **оба тела** (дубли текста).
4. Первый же `snapshotRequest` шлёт `encodeStateAsUpdate(this.doc)`
   ([collab.ts#L205-L212](../web/src/collab.ts#L205-L212)), и сервер
   персистит слитый документ: переписывание агентом незаметно откатано или
   задублировано.

`CachedYDoc` ([offlineCache.ts#L47-L51](../web/src/offlineCache.ts#L47-L51)) не
хранит `gen`. **Фикс:** хранить `gen` рядом со снапшотом и журналом; при
несовпадении с `page.docGen` не применять, а предложить «восстановить оффлайн-
правки как копию» (см. п. 6). **Проверка:** Go/e2e: открыть → закрыть →
`write_content` через API → открыть → нет дублей ни локально, ни на сервере
после `snapshotRequest`.

### 5. Outbox-снапшоты контента обходят `gen`-фенс [подтверждено тестом]
> **Тест (`batch2_outbox.mjs`):** после переписывания страницы агентом на `"AGENT_REWRITE_5"` и открытия её вторым клиентом (живой CRDT-doc на сервере есть) флаш outbox с оффлайн-правок первого клиента перезаписал `pages.content` на `"V1_5 / OFFLINE_STALE_5"`.

Оффлайн-автосейв ([Editor.tsx#L3703-L3714](../web/src/components/Editor.tsx#L3703-L3714))
кладёт в очередь `update-page { content }` с `materialize`, но **без `gen` и
`replaced`**. Реплей ([outbox.ts#L175-L178](../web/src/outbox.ts#L175-L178))
шлёт `?materialize=1` без `gen`, а `materializeGuard`
([docgen.go#L79-L81](../server/docgen.go#L79-L81)) для запроса без `gen`
пропускает запись, если live-doc существует. Итог: устаревшее тело, набранное
оффлайн, перезаписывает `pages.content` поверх переписанного агентом, и
ревизии об этом нет. Ровно та «дверь №1», которую закрывал #79.
**Фикс:** сохранять `gen` в payload и реплеить с ним; `doc_replaced` в outbox
обрабатывать явно (п. 7).

### 6. `onReset` стирает оффлайн-правки, а тост отправляет в историю, где их нет [подтверждено тестом с оговоркой]
> **Тест (`batch1_crdt.mjs`):** при reconnect после 4001 `yjournal` обнулился, в редакторе осталась версия агента `"AGENT_REWRITE_6"`. Если оффлайн-пауза была >1.5 с, текст случайно попадал в ревизии через отклонённый 409 `update-page` (см. п. 5/7); при более короткой сессии (или только CRDT) правки теряются без ревизии. Кроме того, из-за гонки `void dropYDoc` `ydocs` в IDB остался (`ydoc=present`).

[Editor.tsx#L371-L382](../web/src/components/Editor.tsx#L371-L382): на 4001
вызываются `clearJournal` + `dropYDoc`, тост: «Open Version history to recover
your text». Но текст, набранный оффлайн, **никогда не доходил до сервера** и
ревизии не имеет. Типичный сценарий: ноутбук офлайн в поезде, агент тем временем
переписал страницу, при reconnect `?gen=` устарел → 4001 → правки за поездку
стёрты молча.
**Фикс:** перед очисткой сохранить локальный doc: отправить
`materialize&replaced=1` (сервер кладёт это в историю через
`keepRefusedCopy`) или создать страницу-копию «оффлайн-правки (конфликт)».

### 7. Очередь встаёт навсегда на 409 `doc_replaced`, плодя ревизии [подтверждено тестом]
> **Тест (`batch3_outbox_rest.mjs`):** после создания `temp-` страницы оффлайн и набора текста первый `flush()` получил `PATCH /api/pages/<realId>?materialize=1 -> 409` (и записал ревизию). Далее сработал баг п. 8: на следующем `flush()` карта `remap` была пуста, запрос пошёл на `/api/pages/temp-... -> 404` и удалил операцию с потерей текста. Для уже существующей страницы при 409 op остаётся первым в очереди навсегда.

`flush()` ([outbox.ts#L116-L133](../web/src/outbox.ts#L116-L133)) дропает только
400/403/404; всё остальное — «может быть», `attempts++` и `break` (head-of-line).
Сценарий: страница создана оффлайн (temp-id), в неё что-то набрано →
в очереди `create-page`, потом N штук `update-page {content}` без `gen`. При
flush create проходит, а content-op сразу получает 409 (у новой страницы ещё нет
live-doc, guard без `gen` не выполняется,
[pages.go#L919-L944](../server/pages.go#L919-L944)). Op остаётся первым в
очереди → **все последующие записи заблокированы**, а каждая попытка flush
добавляет `keepRefusedCopy` в историю страницы.
**Фикс:** 409/`doc_replaced` → удалить op (сервер уже сохранил копию в
истории) с понятным тостом; блокирующий op не должен держать независимые
(per-page очереди вместо глобальной).

### 8. Remap temp-id живёт только внутри одного `flush()` [подтверждено тестом]
> **Тест (`batch2_outbox.mjs`, `batch3_outbox_rest.mjs`):** `create-page` прошёл, `PATCH` оборван один раз → на следующем `flush()` запрос ушёл на `/api/pages/temp-...`, получил `404` и удалил операцию (`server has 'Offline Title 8' = false`).

`remap` — локальная `Map` в [outbox.ts#L102](../web/src/outbox.ts#L102). Если
`create-page` прошёл, а следующий op упал оффлайн (`break`), при следующем flush
карта пуста: `update-page`/`comment`/`note` с `temp-…` уходят на сервер
как есть → 404/400 → **op удаляется** («Could not sync …»). То же для дочерних
страниц с `parentId = temp-…`. Данные теряются ровно в флапающей сети, для
которой outbox и нужен.
**Фикс:** после успешного create переписывать в IDB `pageId`/`parentId`
оставшихся ops (в той же транзакции, что и `deleteOp`). **Проверка:** тест:
create + 3 edit оффлайн → online только на один запрос → offline → online → все 3
edit на сервере.

### 9. Ошибки IDB при `enqueue` проглатываются, а пользователь видит «Will sync» [подтверждено тестом]
> **Тест (`batch3_outbox_rest.mjs`):** при `QuotaExceededError` в `IDBObjectStore.put` UI показал `"⚠ Will sync when the connection is back"`, хотя `outboxLen = 0`.

`putOp` ([offlineCache.ts#L327-L335](../web/src/offlineCache.ts#L327-L335))
глотает исключение с комментарием «the caller toasts», но `enqueue` об ошибке не
знает, и все вызывающие показывают `Will sync when the connection is back`.
Квота, приватный режим, Safari без IDB → запись потеряна, а UI обещает синк.
**Фикс:** `putOp` пробрасывает ошибку, `enqueue` возвращает `false`, вызывающие
показывают «не сохранено» и не сбрасывают ввод.

### 10. Выход из аккаунта стирает неотправленную очередь без предупреждения [подтверждено тестом]
> **Тест (`batch3c_multitab_logout.mjs`):** оффлайн-нажатие Sign out без предупреждения удалило всю IDB аккаунта (`missingStore: true`), `api.logout()` упал с `Failed to fetch`, пользователь остался на странице (`stillHasEditor=true`) с пустым кэшем.

[App.tsx#L2246-L2258](../web/src/App.tsx#L2246-L2258): `clearOfflineData()`
удаляет IDB аккаунта целиком: outbox, журнал, снапшоты. Нет проверки
`pendingCount()` / непустых журналов и нет диалога «есть N несинхронизированных
изменений». Оффлайн-логаут хуже: данные стёрты, а `api.logout()` падает с
TypeError, необработанно, и пользователь остаётся «внутри» с пустым кэшем.
**Фикс:** перед выходом сделать flush; если что-то осталось — подтверждение
со списком; оффлайн-логаут либо запретить, либо доделать локально.

## P1 — сломанные сценарии и утечки

### 11. Ошибки сервера трактуются как «онлайн, отказ» [подтверждено тестом]
> **Тест (`batch3_outbox_rest.mjs`):** при ответе `502 Bad Gateway` (HTML) на `PATCH` запись в очередь не попала (`outboxLen = 0`).

`isOfflineError = e instanceof TypeError`
([outbox.ts#L45-L49](../web/src/outbox.ts#L45-L49)).
- Сервер за прокси/туннелем (Caddy, nginx, Cloudflare tunnel — штатная
  конфигурация self-host): если сервер лежит, прокси отвечает 502/503/504 →
  `ApiError` → запись **не ставится в очередь**, показывается «not saved».
- Наоборот: любой программный `TypeError` в цепочке `api.*` считается
  оффлайном, и op уходит в очередь навсегда.

**Фикс:** классифицировать по ответу: нет ответа, 502/503/504 или не-JSON от
прокси → «недоступен» (в очередь); TypeError бросать только из обёртки
`fetch`.

### 12. Фолбэк на кэш при любой ошибке, включая 403/404 [подтверждено тестом]
> **Тест (`batch5_remaining.mjs`):** при ответе HTTP `403` на `GET /api/pages/:id` открытая в приложении страница отобразилась из IDB с `.offline-banner` (`hasOfflineBanner=1`).

- Editor ([Editor.tsx#L280-L291](../web/src/components/Editor.tsx#L280-L291)):
  удалённая страница или страница с отозванным доступом открывается из IDB
  как «Offline copy», и в неё можно печатать.
- CollectionView ([CollectionView.tsx#L703-L712](../web/src/components/CollectionView.tsx#L703-L712)):
  то же для базы.

**Фикс:** фолбэк только для сетевых ошибок; на 403/404 — `dropPage`/`dropYDoc`
и штатный экран ошибки.

### 13. SW отдаёт устаревший ответ молча, и приложение считает его свежим [подтверждено тестом]
> **Тест (`batch4_sw_and_coverage.mjs`):** фолбэк SW вернул `status=200` без какого-либо заголовка-маркера (`hasOfflineHeader=false`).

SW network-first ([sw.js#L98-L113](../web/public/sw.js#L98-L113)) при ошибке
сети возвращает кэш как обычный `200`. Тогда:
- `api.getPage` «успешен» → `offlineCopy=false`; баннер виден только при
  `navigator.onLine === false`. Сервер лежит, сеть есть — баннера нет;
- `putCachedPage(p)` перезаписывает IDB-снапшот **старыми данными со свежим
  `savedAt`**, и 30-дневный TTL продлевается бесконечно;
- SW-кэш и IDB дублируют одни и те же данные с разными правилами (TTL, лимиты,
  очистка).

**Фикс:** SW помечает ответ из кэша заголовком (например
`X-Salt-Offline: <savedAt>`); `api` прокидывает флаг; IDB-снапшот обновлять
только от сетевого ответа. В идеале оставить один источник оффлайн-данных.

### 14. Кэш SW не разделён по аккаунтам [подтверждено тестом]
> **Тест (`batch4_sw_and_coverage.mjs`):** после входа User B без нажатия Sign out оффлайн-запрос `/api/pages/<secret_A>` вернул `status=200` с телом страницы User A (`SECRET_USER_A_14`).

IDB разделён по `accountId`, а `salt-data-v1` в Cache API — нет. Чистится только
явным логаутом. При истёкшей сессии (`salt:unauthorized`) или входе другого
пользователя без логаута записи прошлого аккаунта (`/api/pages/:id`,
`/api/me`, базы) остаются, и оффлайн их отдадут любому, кто откроет URL.
**Фикс:** ключ кэша с id аккаунта (или чистка `salt-data*` при смене
`me.user.id` / на 401); `/api/me` из кэша не отдавать, если cookie сессии нет.

### 15. Паттерн SW шире, чем написано в комментарии [подтверждено тестом]
> **Тест (`batch4_sw_and_coverage.mjs`):** в `salt-data-v1` оказались закэшированы `/revisions`, `/comments`, `/notes` и `/backlinks`.

[sw.js#L19-L35](../web/public/sw.js#L19-L35): комментарий обещает, что
«revisions and shares stay network-only», а `startsWith('/api/pages/')` кэширует
и `/revisions`, `/revisions/:id` (полные старые тела), `/comments`, `/notes`,
`/backlinks`, `/references`, `/resolve`. Плюс комментарий-заголовок
продублирован. Нужно решить политику явно (белый список суффиксов) и привести
комментарий к коду.

### 16. Идемпотентность create не атомарна и живёт 24 часа [подтверждено тестом]
> **Тест (`batch6_16_28.mjs`):** 10 параллельных `POST /api/pages` с одним `idempotencyKey` создали 10 разных страниц (`unique page IDs created = 10`).

- [pages.go#L358](../server/pages.go#L358) / [#L451](../server/pages.go#L451):
  проверка ключа и запись результата разнесены, без транзакции и
  уникального резерва. Две вкладки, делающие flush одновременно (у каждой свой
  флаг `flushing`), могут создать страницу дважды. Вики
  ([collaboration.md#L179-L180](../wiki/collaboration.md#L179-L180)) обещает
  «exactly once even from two tabs».
- [ops.go#L122](../server/ops.go#L122) удаляет ключи старше 24 ч. Create,
  который дошёл, но ответ потерялся, и повтор после выходных оффлайн → дубль.

**Фикс:** `INSERT … ON CONFLICT DO NOTHING` резерв ключа до создания; TTL ≥
максимального возраста op (или хранить ключ на странице).

### 17. `comment` и `note` реплеятся без идемпотентности [подтверждено тестом]
> **Тест (`batch3c_multitab_logout.mjs`):** два одновременных флаша из двух вкладок создали 2 одинаковых комментария на сервере.

[outbox.ts#L180-L188](../web/src/outbox.ts#L180-L188): таймаут после коммита на
сервере или две вкладки → дубли комментариев и заметок. Нужен ключ
идемпотентности, как у create.

### 18. Нет межвкладочной координации [подтверждено тестом]
> **Тест (`batch3c_multitab_logout.mjs`):** две вкладки флашили одну очередь одновременно (`Comments count = 2`).

`flushing` — переменная модуля. Нет `navigator.locks` / `BroadcastChannel`:
две вкладки флашат одну очередь параллельно (см. п. 16, 17), а счётчик
`SyncButton` в другой вкладке не обновляется
(`OUTBOX_EVENT` — window-local).
**Фикс:** `navigator.locks.request('salt-outbox', …)` вокруг flush,
`BroadcastChannel` для счётчика и REMAP.

### 19. Оффлайн inline-комментарий теряет якорь [подтверждено тестом]
> **Тест (`batch3b_comments_logout.mjs`):** payload в outbox содержал только `{"body":"Offline inline comment 19"}`; после синка `blockId: ""`, `anchor` отсутствует.

[CommentsPanel.tsx#L135-L136](../web/src/components/CommentsPanel.tsx#L135-L136):
в очередь кладётся только `{ body }`, `blockId` и `anchor` выброшены → после
синка комментарий оказывается на уровне страницы. В очереди он к тому же не
показывается: текст из поля исчез, в списке его нет.

### 20. Stale-снапшот сохраняется после «autosave refused» [подтверждено тестом]
> **Тест (`batch1_crdt.mjs`):** после 409 на materialize в редакторе осталось `"INITIAL_20 STALE_20"`, а в IDB `ydocs` остался снапшот (`len=240`).

`replaced()` (путь через 409 автосейва) ставит `replacedDoc`, но не `reset`.
Cleanup CollabEditor пишет `putYDoc`, если `!p.reset`
([Editor.tsx#L2838](../web/src/components/Editor.tsx#L2838)), то есть
устаревший doc снова попадает в IDB уже после `dropYDoc`. Плюс `dropYDoc` и
`clearJournal` в `onReset` вызываются через `void`, и `setNonce` монтирует новый
редактор, который может прочитать старый снапшот раньше, чем удаление завершится.
**Фикс:** проверять `p.replacedDoc || p.reset`; дождаться удаления до remount.

### 21. Страница, созданная оффлайн, плохо доезжает до CRDT [подтверждено тестом]
> **Тест (`batch2_outbox.mjs`):** оффлайн-созданная страница с текстом `"OFFLINE_CREATED_21"` после ремапа открыта во втором чистом контексте — второй клиент увидел пустое тело (`""`), а после набора в обоих клиентах синхронизация не сошлась (`final1="OFFLINE_CREATED_21"`, `final2=""`).

Для temp-страницы: WebSocket на `/collab/temp-…` переподключается с backoff
вечно; журнал под temp-id **не мигрирует** при create (мигрирует только `ydocs`,
[outbox.ts#L164-L171](../web/src/outbox.ts#L164-L171)); после remap снапшот
применяется до регистрации listener'а (не журналируется), сервер отвечает
`isNew`, сид не выполняется (фрагмент не пуст) → серверный CRDT пуст, пока
пользователь снова не начнёт печатать. Другие клиенты сидят из
`pages.content`, что даёт два независимых набора Y-items, которые при compaction
задваиваются. Нужен e2e: create оффлайн → набрать → online → открыть во втором
контексте → набрать в обоих → нет дублей.

### 22. Каждые 1,5 с оффлайн-набора — новый полный content-op [подтверждено тестом]
> **Тест (`batch3b_comments_logout.mjs`):** 3 коротких ввода с паузой 1,7 с оффлайн → `content ops in outbox = 3`.

Дебаунс материализации кладёт в outbox полный документ на каждую паузу. Час
работы оффлайн — сотни ops с полными телами в IDB, их последовательный реплей и
(с п. 7) сотни ревизий. Оффлайн-снапшоты контента надо **коалесцировать**:
один op на страницу, последний выигрывает.

### 23. `update-page` реплеится вслепую, last-write-wins [подтверждено тестом]
> **Тест (`batch3b_comments_logout.mjs`):** заголовок `"Server Title 23"`, изменённый на сервере во время оффлайна, после reconnect молча перезаписан на `"Offline Title 23"`.

Title, props, position, visibility, workspaceId из очереди перезаписывают то,
что другие (или агент) изменили, пока клиент был оффлайн. Нет базовой версии
(`updatedAt`/`If-Match`) и нет отчёта о конфликте. Минимум — отправлять
`base` и при расхождении писать в audit/показывать «перезаписано вашим
оффлайн-изменением»; для props — патчить только изменённые ключи (это уже
`propsPatch`, но title/visibility/move — целиком).

## P2 — дыры в покрытии оффлайна

### 24. Многие записи вообще не ставятся в очередь [подтверждено тестом]

Оффлайн они либо молча пропадают, либо дают тост, без реплея:

| Действие | Где | Поведение оффлайн |
| --- | --- | --- |

| ссылка на страницу, созданную оффлайн (mention) | [Editor.tsx#L3567-L3604](../web/src/components/Editor.tsx#L3567-L3604) | страница создаётся, ссылка **не вставляется** |

Приоритет внутри: загрузки (вставка картинки оффлайн — частый сценарий; нужно
держать blob в IDB и показывать по `blob:`/temp-URL до синка) → корзина/move →

### 25. Оффлайн-изменения не видны после reload [подтверждено тестом]
> **Тест (`batch4_sw_and_coverage.mjs`):** после оффлайн-reload созданная страница исчезла из сайдбара (`false`), а заголовок откатился к `"Original 25"` вместо `"Edited Offline 25"`.

Очередь и снапшоты не связаны: снапшоты — это то, что пришло с сервера, а
outbox поверх не накладывается.
- Страница или строка, созданная оффлайн, исчезает из дерева/таблицы после
  оффлайн-reload (`/api/pages` из SW её не содержит; `setPages` был только в
  памяти).
- Правки props/title/position оффлайн после reload откатываются к снапшоту,
  хотя op в очереди есть.
- Комментарии и заметки из очереди нигде не показываются.

**Фикс:** при рендере накладывать pending ops на снапшоты (optimistic overlay)
и/или обновлять IDB-снапшоты в момент enqueue.

### 26. Доступно только то, что уже открывали [подтверждено тестом]
> **Тест (`batch4_sw_and_coverage.mjs`):** неоткрытая страница оффлайн показала `"This page could not be loaded.\n\nBack to workspace"`.

Нет «сделать доступным оффлайн» (страница, поддерево, workspace) и нет
префетча (недавние, избранное, открытые вкладки). Неоткрытая страница оффлайн
показывает «This page could not be loaded» с кнопкой «Back to workspace».
Для «доступа оффлайн в целом» это главный пробел.

### 27. Чего нет в кэше, хотя без этого экран не полный [подтверждено тестом]
> **Тест (`batch4_sw_and_coverage.mjs`, `batch5_remaining.mjs`):** `/files/*` картинка онлайн `naturalWidth=1`, оффлайн `-1` (не загрузилась); `/api/search` упал с `TypeError: Failed to fetch`; `mdiSet` в `salt-shell-v1` отсутствует без открытия icon picker (`false`).

- `/files/*`: картинки, обложки, вложения, аватары. Документ оффлайн с
  битыми картинками; обложки и `thumb` в списках пустые;
- `/api/tag-colors`, `/api/comment-counts`, `/api/favorites`, `/api/tags`,
  `/api/users` (people-свойства, упоминания), `/api/me/prefs`;
- `/api/search`: оффлайн-поиска нет совсем, хотя локальный поиск по
  закэшированным страницам и заголовкам дерева возможен;
- lazy-чанки не прекэшируются (`mdiLoader.ts` → `mdiSet`, плюс динамические
  импорты внутри библиотек, если есть): иконпикер оффлайн не открывается, если не
  открывался онлайн после деплоя.

### 28. Нет ретраев, пока сеть «есть», а сервер нет [подтверждено тестом]
> **Тест (`batch6_16_28.mjs`):** после сбоя `PATCH` (после 3-секундного boot-таймера) запись осталась в `outbox` (`before=1`), и за 6 с с доступным сервером при `navigator.onLine === true` не ушла (`after=1`).

`initOutbox` флашит только на `online` и один раз через 3 с после загрузки
([outbox.ts#L223-L230](../web/src/outbox.ts#L223-L230)). Если сервер лежал, а
сеть была, события `online` не будет, и очередь стоит до ручного клика или
reload. Нужно: ретрай с backoff, флаш при успешном collab-`synced`/SSE-hello,
`visibilitychange`; Background Sync там, где он есть (Chromium).

### 29. Нет общего индикатора «связь с сервером» [подтверждено тестом]
> **Тест (`batch4_sw_and_coverage.mjs`):** при наборе оффлайн в `yjournal` (до таймера outbox) `.sync-badge` отсутствует (`count = 0`).

`useOnline` — только `navigator.onLine`. Состояние collab-сокета, SSE и ошибки
API в один индикатор не сведены. Сокет мёртв, сеть есть → пользователь
не знает, что печатает в журнал. `SyncButton` не считает непустые
CRDT-журналы, поэтому «0 changes waiting», хотя текст страницы не доехал.

### 30. `SyncButton` нельзя использовать для разбора проблем [подтверждено тестом]
> **Тест (`batch4_sw_and_coverage.mjs`):** при 10 операциях в очереди панель показала 8 `<li>` и текст `"…and 2 more"`, без ошибок/кнопок.

Список ограничен 8 метками; нет причины, почему op висит (последняя ошибка,
`attempts`), нет «повторить», «отбросить», «открыть страницу». Застрявший op
(п. 7) блокирует очередь, и пользователю нечем его снять.

### 31. Хранилище может быть выселено, квоты не контролируются [подтверждено тестом]
> **Тест (`batch4_sw_and_coverage.mjs`):** `navigator.storage.persisted()` вернул `false`.

- Нет `navigator.storage.persist()`: Safari (не установленное PWA) удаляет
  script-writable хранилище через 7 дней без визита, Chromium выселяет под
  давлением, **вместе с outbox**.
- `ydocs` и `yjournal` никогда не прунятся (`prune` есть только для `pages`
  и `collections`); SW `/assets/*` копится между деплоями, потому что `SHELL`
  не версионируется; `salt-data-v1` без лимита.
- Снапшот базы хранит все строки на каждый ключ фильтра: 50 баз × N фильтров
  × 50k строк.
- Нет `storage.estimate()` и реакции на `QuotaExceededError` (см. п. 9).

### 32. Без secure context оффлайна нет вообще [подтверждено тестом]
> **Тест (`batch5b_28_32_33.mjs`):** на `http://salt.test:<port>` `isSecureContext=false`, `swController=false`, оффлайн-перезагрузка упала с `net::ERR_INTERNET_DISCONNECTED`.

SW регистрируется только при `window.isSecureContext`
([main.tsx#L78](../web/src/main.tsx#L78)). Self-host в LAN по `http://192.168…`
(частый случай) не получает ни shell, ни API-кэша: оффлайн-перезагрузка даёт
ошибку браузера, а при недоступном `/api/me` — `setLoadError(true)`. Это надо
хотя бы задокументировать и показать в UI.

### 33. «Lie-fi»: network-first без таймаута [подтверждено тестом]
> **Тест (`test_33_liefi.mjs`):** через HTTP-прокси с 5-секундным зависанием `/api/pages/:id` страница висела в `.editor-loading` 5348 мс, прежде чем отрисоваться из кэша.

На плохой связи fetch в SW висит до сетевого таймаута браузера (десятки
секунд), только потом срабатывает фолбэк. Нужна гонка с таймаутом (3–5 с) для
навигаций и снапшотов (stale-while-revalidate для `/api/pages` и `/api/me`).

### 34. Снапшот теряется при закрытии вкладки [подтверждено тестом]
> **Тест (`batch1_crdt.mjs`):** удалённая правка `"REMOTE_ONLY_34"` уже отобразилась у первого клиента, но через 2 с `ydocs` в IDB всё ещё был `null` (до unmount не сохраняется).

`putYDoc` дебаунсится на 1 с, а финальная запись в cleanup эффекта асинхронна и
на `pagehide` на мобильных может не успеть. Удалённые изменения, увиденные за
сессию, в снапшот не пишутся, пока нет локальной правки или unmount (убитая ОС
вкладка → оффлайн откроется более старая версия). Добавить запись на
`pagehide`/`visibilitychange: hidden`.

### 36. Тестовое покрытие оффлайна — один happy path [код]
[web/tests/offline.mjs](../web/tests/offline.mjs) (37 строк) не ловит ни п. 1,
ни п. 2–8, потому что сверяет материализованный `content`, а не CRDT, и не
использует второй клиент. Минимальный набор сценариев, которых не хватает:

1. Набор оффлайн (≥200 символов) → online → **второй чистый контекст** видит
   ровно тот же текст (ловит п. 1–3).
2. Набор оффлайн → закрыть вкладку → открыть оффлайн → online → второй
   контекст (journal после reload).
3. Открыть → закрыть → `write_content` через API → открыть → нет дублей после
   compaction (п. 4).
4. Оффлайн-правки, пока агент переписал страницу → reconnect → правки
   сохранены как копия/ревизия (п. 5, 6).
5. Create + edit + comment оффлайн, flush прерывается после create → всё
   доезжает (п. 8), очередь не стоит (п. 7).
6. Две вкладки флашат одну очередь → одна страница, один комментарий
   (п. 16–18).
7. Сервер отвечает 502 (прокси) → запись в очереди, а не «not saved» (п. 11).
8. 403/404 на закэшированную страницу → не открывается как offline copy
   (п. 12).
9. Логаут с непустой очередью → предупреждение (п. 10); смена аккаунта без
   логаута → нет чужих данных оффлайн (п. 14).
10. Оффлайн-reload после создания строки/страницы → она видна (п. 25).

Плюс Go-тесты: атомарность идемпотентности (параллельные create с одним
ключом), materialize без `gen` для страницы без live-doc.

## Предлагаемый порядок работ

1. **Целостность CRDT-пути** (п. 1–4, 6, 20): одна задача, общий тест
   «второй клиент видит то же». Скорее всего, проще заменить журнал полной
   отправкой state с `gen`-проверкой, чем латать журнал.
2. **Outbox-корректность** (п. 5, 7–9, 11, 16–19, 22): персистентный remap,
   коалесцирование контента, `gen` в content-op, классификация ошибок, Web Locks,
   идемпотентность comment/note.
3. **Безопасность данных аккаунта** (п. 10, 12, 14, 15).
4. **Видимость оффлайн-изменений** (п. 13, 25, 29, 30).
5. **Покрытие** (п. 24, 26, 27, 28, 33): файлы, префетч и «доступно оффлайн»,
   очередь для остальных записей, ретраи.
6. **Хранилище и доки** (п. 31, 32, 34, 35).

Каждый блок — отдельный PR с fail-before/pass-after тестом из списка п. 36.
